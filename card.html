Card

A card is a container for related information. It can hold text, media such as photos or illustrations, and interactive content. Cards can be arranged in stacks, columns or grids.

Product usage

Cards are most common on home pages and dashboards, such as the Teladoc Health member home and the provider home. They can also appear in flows.

Buttons in cards

Cards do many jobs in Teladoc Health products, so button guidance depends on the card's context. Follow the general button placement guidance as well as the guidance below.

Interaction

Cards are static containers: the whole card is never a tap target. To make a card interactive, add interactive content in the header (when there's no image at the top), the main content slot or the footer.

  • Header: the optional header action uses the default tap target of its icon button or tertiary button.
  • Main content slot: you can add more tap targets here, such as links or nav-list items.
  • Footer: footer actions use the default tap targets of their primary, secondary or tertiary buttons.

Accessibility

Using a card on a page still needs an annotated design review of the page-level design.

Header and footer buttons

  • An icon button in the header needs a description of what it does as extra screen reader context: <Header>, <Additional context>, such as "Button, More information".
  • Header and footer buttons can use the button or link role, depending on the action. Add context when the visible label isn't enough: <Visible label>, <Additional context>.

Links and form inputs

  • Don't put inline text links in headers. They're fine in the main content slot.
  • Include interactive content in the main content slot in the tab order.
  • Read each input's label with its field, separately from the card header.

Images

  • Most card images are decorative. On web, use alt=""; on mobile, they need no image description.
  • If an image carries meaning, describe it (alt on web, an image description on mobile) and include it in the mobile swipe order.

Headings and order

  • The header's heading level, and the tab or swipe order of every control, depend on the surrounding page.
  • In code, cards render as <section>. Set headerAs to keep heading levels in order (default h3), and pass headerId so the section is labeled by its header.

Content guidelines

Headers

  • Summarize what's in the card.
  • Don't use inline text links in header text.

Footers

  • Follow the Button content guidelines.

Code vs. Figma.
  • Figma has an "Additional content" property. In code, pass more than one child to a spot card: everything after the first child is full width.
  • Mobile or desktop layout follows the card's own width, not a platform prop: under 480px the footer stacks and buttons fill the width. There's no override yet to make a single mobile button hug its label.
  • Footer buttons render in the order you pass them, so reordering or right-aligning them on desktop is up to the page.
