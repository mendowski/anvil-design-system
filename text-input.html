Text input

Text input lets people enter a single line of text, such as contact or payment information. It usually sits in forms and dialogs, grouped with other inputs, and has states with optional helper text, icons, placeholder and units.

Usage

Pair text inputs with an action that applies the changes, such as a Save or Next button.

Typical information

  • First and last name
  • Username or email address
  • Address, such as street and ZIP code

Product usage

  • Request a visit: scheduling
  • New and existing members: signing in and registering
  • Chronic Condition Management: entering weight, calories and blood sugar

Used with

  • Icons
  • Inline message, for warning and critical states

Variants and options

Required fields

Forms show "* Required" at the top: fields with an asterisk must be filled, and fields without one are optional.

All fields required

  • Every label gets the asterisk. The form header already says fields are required, but the asterisk is still needed for accessibility, clarity and consistency.

Some fields required

  • Required fields get an asterisk (*). Optional fields have no marker.
  • Don't use an "(optional)" label.

Validation

  • Validate inline, as people go.
  • A required field shows no error until people have been in it and left it empty. When they start typing, the "required" error disappears right away.
  • When people leave a field, validate it immediately and show an error if the input is invalid.
  • Don't validate on every keystroke: a phone number shouldn't show an error while people are still typing it.
  • Avoid validating the whole form on submit unless it's technically needed, such as server-side checks. Showing every error at once after Submit overwhelms people.

Units

Use units for information such as an A1c percentage, or height and weight in local units. The unit is shown next to what people type.

Placement

Grouping

  • A single input works in step-by-step flows, but forms and modals usually group several.
  • Stack inputs in one or more containers to help people focus.
  • Use the space-between-forms token between inputs. Sections can vary, as long as they follow the spacing guidelines.

Horizontal layout

Put similar inputs side by side when they ask for related information (first and last name) and the answers are short.

Interaction

Accessibility

Using text inputs on a page still needs an annotated design review of the page-level design.

Web

  • Every visible text must be announced. Screen readers announce inputs as "edit text".
  • Every input can be reached with Tab. Disabled inputs are skipped (don't annotate a tab stop), but screen readers can read them with the arrow keys.
  • Read-only fields: VoiceOver says "text", NVDA "read only".
  • Error icons are background images, so they don't need alt text.

iOS and Android

  • The order varies: iOS may read label, helper text, then value; Android may read value, label, then helper text.
  • VoiceOver says "text field" and TalkBack "edit box". Disabled: "dimmed" (iOS) or "disabled" (Android). Read-only: "read-only" (iOS) or "disabled" (Android).
  • Empty, required field with an error: iOS reads the error, then "double tap to edit"; Android reads label, "Required", helper text, error, "Input box, double tap to activate".
  • Use one swipe-order annotation per input and its label, since they're grouped.

In code

  • The label is a real <label>, and helper text and messages are linked with aria-describedby. Errors set aria-invalid.
  • Units are hidden from screen readers; put the full unit in the label, such as "Weight (pounds)".

Content guidelines

  • Format units following the editorial style guide's guidance on abbreviations and acronyms.
  • Don't rely on placeholder text for critical information or instructions. Use helper text for hints.

Code vs. Figma.
  • Code supports an icon before the text only. Figma (v5.5.1) also has an icon after, and both, including interactive icons such as clear or copy.
  • FlowUI is still missing units and the icon updates.
