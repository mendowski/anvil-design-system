Global header

The global header is the top bar of every screen. One component covers mobile and web, so headers stay consistent across platforms while each platform gets its own layout. Its nested parts differ by platform to support animation and sizing.

1024DesktopLeft: navigation items in full. Right: the expanded avatar list, and icons for search and language.

Focused task and progress tracker headers follow the same widths. At 150% and 200% zoom, check the header at 390, 894, 1024 and 1440.

Guidance

Default

  • Use it on every page reached from the global footer, which is always shown with it. Pages with the default header use the tab bar to move between the main sections.
  • Every menu item goes to a new page or opens a menu. Get care goes to a new page.
  • The language selector is a dropdown, on web only.
  • The secondary menu goes to a new page. It's for Chronic Condition Management and Mental Health, and gives section navigation separate from the tab bar.

Focused task

  • Don't show the global footer: not in signed-out flows, second- and third-level flows, or menu pages.
  • Back goes to the page before.
  • Close leaves the sub-flow or cancels what the flow started. The product decides where the flow begins.

Progress tracker

  • Never show the global footer. Pages show only a Next or Continue button to move forward.
  • Back goes to the page or step before. On web it usually appears after the first screen, and should work like the browser's own Back button: it's a courtesy, not a different path.
  • Close is always available, and leaves the flow.

Breaking flows into steps

  • Break long or complicated tasks into meaningful, small steps. Test the structure with UX research, and work with engineering on how steps map to the component.
  • Don't treat every page as a step. The number of pages can be unknown, too high, change with what people enter, or mix required, optional and revealed sections.
  • If a step is always one page, the tracker can turn into decoration, discourage people, or show wrong numbers or change scale midway.
  • Never mislead people about where they are or how many steps are left.

Scroll animations (default to scrolled) are for the iOS and Android apps only, not web mobile.

Writing step labels

The progress tracker needs custom step labels; write them with the Content team. Test any labels in US English and US Spanish, and if you can, in Dutch, Catalan and French.

Also

  • Avoid abbreviations and acronyms unless they're widely understood, like Info or Meds. If in doubt, spell it out.
  • With one dynamic step label, the value reads "Step N of N". It can use other units, such as "NN% completed".
  • Keep the Back label as "Back". If you must change it, keep it short, clear about where it goes, the same across the flow, and check it in Spanish.

Accessibility

Using the header on a page still needs an annotated design review of the page-level design.

Links or buttons

  • Code a menu item as a link if it goes to a new page, or a button if it acts on the current page.

Screen readers

  • Teams need to be able to change the screen reader text for the menu icon buttons.
  • On web, announce each menu item's state, "expanded" or "collapsed". Most screen readers also announce "List with N items" on the first item of an open menu.
  • Badges are read as part of the label, such as "Messages, 2 new".

Order and size

  • On mobile, Back comes last in the screen's swipe order.
  • Tap targets are at least 44 × 44px.
  • The header renders as <header>, with the main nav as a <nav> named "Main", and the progress bar as a progressbar.

Code vs. Figma.
  • Not in the code component yet: the secondary menu (CCM and Mental Health), the focused task Info button, search, and the expanded avatar list at 1024px.
  • The header switches between mobile and desktop at 768px of its own width. The 834, 1024 and 1140 steps aren't built.
  • The desktop focused header shows the full logo where Figma shows the Teladoc Health connector mark.
  • Nav items support default, hover, focus and current. Pressed and disabled aren't built, and mobile icon buttons have no forced states for docs.
  • Menus, the intent-to-exit modal and transitions (including the 300ms progress fill) are up to the page.
