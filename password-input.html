Password input

Password input is a text field for signing in to a Teladoc Health account or creating a secure password. It protects sensitive information, such as health profiles, prescriptions and services, from brute-force attacks using Teladoc Health's security rules.

Variants and options

Strength

Password creation tools show a strength indicator and a list of requirements, to guide people to a secure password and nudge them toward a stronger one (optional).

Strength and security

Password rules follow OWASP and HIVE guidance and Teladoc Health's security team.

Composing a password

  • Length matters most: the longer, the better.
  • HIVE requires 8 characters minimum, and OWASP 2.1.1 12 or more. Teladoc Health follows HIVE to reduce friction, and encourages 12 or more with the strength indicator.
  • OWASP 2.1.9 and HIVE don't require complexity, but with an 8-character minimum HIVE recommends it. The minimum requirements include an upper and lower case letter, a symbol and a number.
  • With every complexity rule, an 8-character password takes about 5 minutes to brute-force, 10 characters about two weeks, and 11 or more about three years.
  • Unicode characters, including spaces and emoji, are allowed (OWASP 2.1.4, HIVE).
  • Turn on multi-factor authentication and breached-password detection too (OWASP 2.1.7, HIVE).

Personal information

  • Names, usernames and email addresses aren't allowed. Developers set the forbidden words, such as name, company name and email (excludeWords in code).

Breached passwords

  • On sign-in, creation and reset, check the password against a dataset of breached passwords and reject any match (OWASP 2.1.7, HIVE).

Interaction

Tap targets

  1. Tapping the text field focuses it for typing.
  2. Tapping Show or Hide toggles whether the password is visible.

Create password

  • The strength indicator and requirements aren't interactive, but update as people type.
  • They're hidden until the field gets focus.
  • They only stay once people have typed something. If people leave without typing, they hide again. Once there's any text, they stay even after leaving the field. If people clear the field, they hide when it loses focus.
  • When every requirement is met, the requirements hide and the "Strong" strength and bar stay.

Platforms

  • Following Nielsen Norman Group guidance, the password is obscured by default on every platform, and people can always show or hide it while signing in or creating a password.
  • On native, hover and focus apply to the whole input rather than separately to the field and the button.

Accessibility

Using a password input on a page still needs an annotated design review of the page-level design.

In code

  • The Show / Hide button is a real button with aria-pressed and aria-controls, named "Show password" or "Hide password".
  • Strength changes are announced politely (aria-live).
  • Each requirement includes hidden "met" or "not met" text, so its status doesn't rely on the icon.
  • Sign-in uses autocomplete="current-password" and create uses new-password, so password managers work.

Annotations

  • Annotate both the obscured and visible states, and the toggle, on web and mobile, for sign-in and create.

Code vs. Figma.
  • In code, the strength indicator and requirements are always shown in create mode. Hiding them until focus, and hiding the requirements once the password is strong, aren't built yet.
  • Code works out strength from the requirements met (under half: very weak; half or more: average; all: strong). The guideline also uses length: 10, 11 and 12+ characters.
  • The default requirement is 10 characters; the guideline's minimum is 8 (HIVE).
  • Breached-password checks and the "Password required" error need the page or the server.
